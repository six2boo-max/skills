# Lean Research — 저비용 딥리서치

목표: 적은 토큰으로 출처가 달린 정확한 결론을 내는 것.
웹 페이지 원문, 반복된 맥락, 서브에이전트에 토큰이 가장 많이 든다. 이 셋을 줄인다.

## 0. 예산 정하기

요청을 보고 단계를 하나 고른다. 사용자가 단계를 말하면 그대로 따른다.

| 단계 | 언제 | 검색 | 페이지 열기 |
|---|---|---|---|
| quick | 사실 확인, 단순 비교 | 최대 4회 | 최대 2개 |
| standard (기본) | 일반적인 조사·비교 | 최대 8회 | 최대 4개 |
| deep | 사용자가 "깊게/자세히"를 요청했을 때 | 최대 15회 | 최대 8개 |

상한에 닿으면 멈추고, 남은 공백은 보고서에 적는다. 상한을 넘기려면 먼저 사용자에게 묻는다.

## 1. 계획은 한 번만 (검색 전에)

- 질문을 하위 질문 2~5개로 나누고, 각각에 쓸 검색어를 정한다.
- 질문이 정말 모호할 때만 되묻는다. 그 밖에는 합리적으로 가정하고 그 가정을 보고서에 한 줄로 적는다.
- 계획은 머릿속(생각)에서만 세운다. 사용자에게 계획을 길게 설명하지 않는다.

## 2. 검색 규칙

- **한 번에 묶어서**: 서로 독립적인 검색은 한 턴에 병렬로 보낸다. 하나씩 순서대로 보내지 않는다.
- **기본은 `standard` 모드**: 결과가 빈약하거나, 오래됐거나, 엉뚱할 때만 그 검색어를 `extended`로 다시 한다. 아주 최근 소식, 가격, 니치한 사실은 처음부터 `extended`를 써도 된다.
- **스니펫 먼저**: 검색 결과의 요약 문구로 답이 되면 페이지를 열지 않는다.
- **검색어는 구체적으로**: 연도, 제품명, 원문 언어(영어 자료가 많은 주제는 영어)로 쓴다. 같은 뜻의 검색어를 반복하지 않는다.

## 3. 페이지 읽기 규칙

- 페이지는 `WebFetch`로 열되, **뽑아낼 내용을 정확히 지정**하는 prompt를 쓴다.
  - 좋은 예: "2026년 요금제별 월 가격과 사용량 한도만 표로 뽑아줘"
  - 나쁜 예: "이 페이지 요약해줘"
- 공식 문서, 1차 자료(논문·발표·공식 블로그), 신뢰도 높은 언론을 우선한다. SEO용 모음 글은 피한다.
- 같은 사이트를 두 번 이상 열지 않는다.

## 4. 하지 말 것

- 서브에이전트(Agent 도구)나 `deep-research` 스킬을 부르지 않는다. 이 스킬을 쓰는 이유가 그 비용을 피하는 것이다.
- 이미 찾은 사실을 다시 검색하지 않는다.
- 페이지 원문이나 긴 인용문을 그대로 붙여넣지 않는다.

## 5. 메모와 종료 조건

- 찾은 내용은 `사실 — 출처 URL` 한 줄 형식으로만 머릿속에 정리한다.
- 하위 질문마다 **서로 다른 출처 2개가 일치**하면 그 질문은 끝낸다. 1차 자료(공식 문서 등)라면 1개로 충분하다.
- 출처끼리 말이 다르면 더 최신이고 더 1차인 자료를 따르고, 차이는 보고서에 적는다.
- 모든 하위 질문이 끝났거나 예산에 닿으면 바로 보고서를 쓴다.

## 6. 보고서 형식

사용자가 쓴 언어로, 아래 순서대로 짧게 쓴다.

```
## 결론
(2~4문장. 질문에 대한 직접적인 답)

## 핵심 근거
- 근거 1 [1]
- 근거 2 [2]
(하위 질문별로, 필요하면 표로)

## 한계·불확실한 점
- 확인하지 못했거나 출처끼리 다른 부분, 내가 세운 가정

## 출처
[1] 제목 — URL (날짜)
[2] ...
```

- 수치·날짜·가격에는 반드시 출처 번호를 단다.
- 사용자가 문서나 페이지로 달라고 할 때만 파일이나 아티팩트로 만든다. 기본은 채팅 답변이다.
- 마지막에 한 줄로 사용량을 적는다. 예: `검색 6회 · 페이지 3개 (standard)`
